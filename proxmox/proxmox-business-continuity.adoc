= Learn about Proxmox VE business continuity with SnapMirror active sync
:hardbreaks:
:icons: font
:linkattrs:
:imagesdir: ../media/

[.lead]
Enterprises that run business-critical virtual machines (VMs) on Proxmox Virtual Environment (VE), and service providers that host customer VMs on Proxmox VE, need those VMs to keep running when a storage system or an entire data center goes offline. ONTAP SnapMirror active sync synchronously replicates the shared storage of a Proxmox VE cluster stretched across two sites and automatically fails over storage to the surviving site. You get a zero recovery point objective (RPO), automated recovery without scripts or runbooks, and the same shared storage at both sites, so Proxmox VE high availability (HA) can restart VMs without any storage reconfiguration. For NFS shared storage, the solution uses SnapMirror active sync for NAS.

== Customer challenges

Building storage and site resilience for Proxmox VE with native tools alone is difficult:

* *Data loss after a site failure.* Proxmox VE storage replication and Proxmox Backup Server are asynchronous. Changes made since the last replication or backup are lost when the primary site fails.
* *Manual, slow recovery.* Recovering at a secondary site usually means promoting replicas, mounting storage under a different address, updating `/etc/pve/storage.cfg`, and restarting VMs. Each manual step adds downtime and the risk of error during an outage.
* *Complex stretched storage.* Software-defined stretched storage keeps extra replicas of every object at both sites, consumes compute and network resources on every node, and needs its own tie-breaker design.
* *Split-brain risk.* A two-site cluster with an even number of nodes loses quorum, or splits, when the inter-site link fails, unless a third-site witness decides which site survives.
* *Routed networks between sites.* Many data centers don't stretch layer 2 VLANs between sites, so a storage IP address from one site isn't reachable at the other site after a failover.

=== Service provider challenges

Service providers that build cloud services on Proxmox VE face the same challenges, with tenant service level agreements (SLAs) on top:

* *The storage system is a shared point of failure.* Proxmox VE HA protects tenant VMs from a host failure, but not from a failure of the storage system that hosts their disks. One storage outage affects every tenant on that system.
* *No way to sell higher availability.* Without synchronous replication and automatic storage failover, a provider can't offer a premium availability tier with zero data loss and stronger uptime commitments.
* *Tenant isolation during recovery.* Recovery, maintenance, and disaster recovery tests must affect only the tenants involved, not the whole platform.

=== Enterprise challenges

Enterprises that move mission-critical workloads from other hypervisors to Proxmox VE expect the same site resilience they had before, such as zero data loss for databases and line-of-business applications and recovery without a manual runbook. Meeting that expectation with Proxmox VE native tools alone takes significant design, scripting, and operational effort.

== Solution overview

The solution combines a Proxmox VE stretch cluster with SnapMirror active sync on NetApp AFF systems at two sites:

* *Zero RPO.* ONTAP replicates every write to the shared storage synchronously from the primary cluster at site A to the secondary cluster at site B.
* *Same shared storage at both sites.* After a failover, the secondary cluster presents the same storage to Proxmox VE, so the storage definitions in `/etc/pve/storage.cfg` stay valid.
* *Automatic failover.* ONTAP Mediator, or ONTAP Cloud Mediator, acts as a witness in a third failure domain. When the primary storage or site fails, ONTAP fails over to site B without manual intervention.
* *Granular control.* You choose which workloads to protect, and you can fail over workloads individually, for example to move one tenant or application for site maintenance.
* *Use of the secondary copy.* You can clone the secondary copy for development, testing, or disaster recovery testing without affecting replication.

The following diagram shows the solution architecture with NFS shared storage.

image:proxmox-business-continuity-001.png["Architecture of a Proxmox VE stretch cluster with SnapMirror active sync for NAS. The components are described after the diagram."]

Site A and site B::
Each site has an AFF two-node cluster and half of the Proxmox VE nodes. The primary cluster at site A serves the shared storage to all Proxmox VE nodes. Nodes at site B reach the primary cluster across the inter-site network. With NFS storage, the secondary SVM at site B stays dormant until a failover occurs.

Site C::
A third failure domain hosts ONTAP Mediator and the corosync QDevice daemon (`corosync-qnetd`). ONTAP Mediator helps ONTAP decide which cluster serves data. The QDevice provides an extra vote so that the Proxmox VE cluster keeps quorum when one site fails. You can use ONTAP Cloud Mediator in the NetApp Console instead of an on-premises ONTAP Mediator.

Proxmox VE stretch cluster::
All Proxmox VE nodes belong to one cluster and share the same storage definitions. Proxmox VE HA restarts VMs from a failed site on the surviving nodes. Storage Manager for Proxmox (SMP) runs as an HA VM on the cluster to provision shared storage and to back up, restore, and clone VMs.

=== Benefits for service providers

* *VM availability beyond host HA.* Tenant VMs keep running when the storage system that hosts their disks fails. ONTAP fails over to the second AFF cluster, and the VMs resume I/O on the same shared storage without a restart.
* *A premium availability tier.* You can offer a zero RPO, storage-resilient VM service as an add-on, alongside standard tiers on unprotected storage in the same clusters.
* *Per-tenant protection and failover.* With separate protected storage for each tenant or service tier, you protect, fail over, and test disaster recovery for each tenant independently, without affecting other tenants.
* *Better use of both sites.* You can make some workloads primary at site A and others primary at site B, so both data centers serve active workloads.

=== Benefits for enterprises

* *Zero data loss for business-critical VMs* during a storage or site failure.
* *Automated recovery* without scripts, storage remounts, or changes to `/etc/pve/storage.cfg`.
* *Built into ONTAP*, with no extra software layer on the Proxmox VE nodes.
* *Day-to-day operations from one interface.* Storage Manager for Proxmox provisions the protected shared storage and backs up, restores, and clones VMs with ONTAP snapshots and FlexClone technology.

== How the solution responds to failures

ONTAP and Proxmox VE make independent quorum decisions. The design aligns them so that both choose the same surviving site.

[cols="2,3,3" options="header"]
|===
| Event
| ONTAP behavior
| Proxmox VE behavior

| Site A fails
| ONTAP Mediator confirms the failure, and ONTAP automatically fails over the shared storage to cluster B.
| Site B nodes and the QDevice keep quorum. HA fences the site A nodes and restarts their VMs on site B nodes. VMs already on site B resume I/O after the storage failover.

| AFF cluster A fails, Proxmox VE nodes at site A keep running
| ONTAP Mediator confirms that cluster A is unreachable, and ONTAP automatically fails over the shared storage to cluster B.
| No quorum change and no VM restart. VMs on all nodes resume I/O on the same shared storage after the storage failover, with site A nodes reaching cluster B across the inter-site network.

| Site B fails
| Cluster A continues to serve data. Replication resumes when site B returns.
| Site A nodes and the QDevice keep quorum. HA restarts the site B VMs on site A nodes.

| Inter-site link fails
| Cluster A continues to serve data. No failover occurs.
| The QDevice gives its vote to the site A partition when the tie breaker is aligned with the primary cluster. Site B nodes lose quorum and self-fence, and HA restarts their VMs on site A.

| Site C fails
| Replication continues with zero data loss, but automatic and planned failovers aren't possible until the mediator is available.
| The cluster keeps quorum with the votes of the four nodes. No VMs are affected.

| One Proxmox VE node fails
| No impact.
| HA restarts the VMs from that node on other nodes, preferring nodes at the same site.
|===

=== Storage system failure

A storage system failure is the case that host-level HA alone can't handle, and the case where SnapMirror active sync adds the most value for service providers. The following diagram shows the state after AFF cluster A fails while every Proxmox VE node stays online, using NFS shared storage.

image:proxmox-business-continuity-002.png["State after AFF cluster A fails. All Proxmox VE nodes keep running and access the NFS shared storage on the secondary SVM at site B. The numbered items are described after the diagram."]

. AFF cluster A becomes unavailable. The Proxmox VE nodes at site A keep running, so the cluster doesn't lose quorum and HA doesn't fence any node.
. ONTAP Mediator confirms that cluster A is unreachable, and ONTAP activates the secondary SVM on cluster B with the same NFS LIF address, volumes, and export policies.
. All Proxmox VE nodes resume I/O on the same shared storage. Site B nodes reach cluster B locally, and site A nodes reach it across the inter-site network. VMs pause I/O during the failover and keep running without a restart.

When cluster A returns, replication resumes. Plan the failback to cluster A during a maintenance window so that site A VMs access local storage again.

=== Site failure

During a site failure, both the storage system and the Proxmox VE nodes at that site go offline. ONTAP fails over the shared storage to the surviving cluster, and Proxmox VE HA restarts the VMs from the failed site on the surviving nodes, as described in the table.

== Choose between SnapMirror active sync and MetroCluster

NetApp MetroCluster configurations also deliver zero RPO and automatic recovery for a Proxmox VE stretch cluster. The two solutions differ in what they protect:

* *MetroCluster protects all workloads.* MetroCluster combines array-based clustering with synchronous replication. It mirrors every aggregate, the nonvolatile cache, and the configuration of every SVM to the partner site, so all shared storage on the cluster is protected without per-workload setup.
* *SnapMirror active sync protects a subset of workloads.* You choose which SVMs or volumes to protect, and you can fail over each one independently. Unprotected workloads can share the same clusters.

=== MetroCluster architecture with Proxmox VE

The following diagram shows a Proxmox VE stretch cluster with a four-node MetroCluster IP configuration and NFS shared storage.

image:proxmox-business-continuity-003.png["Proxmox VE stretch cluster with a four-node MetroCluster IP configuration. Each site serves its own SVM and holds a stopped mirror of the SVM at the other site. The components are described after the diagram."]

MetroCluster IP clusters::
Each site has an HA pair with mirrored aggregates. The MetroCluster IP back-end network mirrors data and the nonvolatile cache to the partner site synchronously.

SVMs at both sites::
Each site can serve its own SVMs. For each SVM, MetroCluster keeps a stopped mirror SVM with the `-mc` suffix at the partner site, with the same configuration and LIF addresses.

Switchover::
If a site fails, ONTAP Mediator or MetroCluster Tiebreaker at site C enables an automatic switchover. The mirror SVMs at the surviving site start and serve all shared storage with the same NFS addresses, and Proxmox VE HA restarts the VMs from the failed site. A single controller failure is handled by a local HA takeover, without a switchover. After you repair the failed site, you heal the aggregates and switch back.

=== Selection guidance

* Choose MetroCluster when all, or nearly all, workloads on the storage need zero RPO, for example when an enterprise runs only mission-critical VMs on the cluster, or a service provider offers the same availability tier to every tenant. You get one protection domain without per-workload configuration.
* Choose SnapMirror active sync when only a subset of workloads needs zero RPO, for example a premium tier for some tenants, or when you need to fail over or test disaster recovery for one tenant or application at a time.
* SnapMirror active sync for NAS isn't supported on a MetroCluster configuration. Use one solution for each pair of clusters.
* The corosync, QDevice, and HA guidance in this solution applies to both. With MetroCluster, align the QDevice tie breaker with the site that keeps serving data when the inter-site link fails, and use HA node affinity rules to keep VMs at the same site as their active SVM.
* MetroCluster IP also supports VIP LIFs with BGP for layer 3 networks between sites.

== Corosync considerations for a Proxmox VE stretch cluster

Proxmox VE uses corosync for cluster membership and quorum. Corosync is more sensitive to the inter-site network than SnapMirror active sync, so plan the cluster network first.

=== Latency and network design

* SnapMirror active sync requires an inter-cluster round-trip time (RTT) under 10 ms. Proxmox recommends a corosync latency under 5 ms between all nodes, so the corosync requirement sets the distance limit for the solution.
* Corosync needs low, consistent latency rather than high bandwidth. Use a dedicated network for corosync, separate from storage and live migration traffic, so that storage bursts don't cause corosync timeouts.
* Configure at least two corosync links (for example, link 0 and link 1) on separate physical paths between the sites. Corosync uses Kronosnet to switch links automatically if one path fails.

=== Quorum with a QDevice at a third site

Split the Proxmox VE nodes evenly between site A and site B, and add a QDevice at site C. With four nodes and a QDevice, the cluster has five votes and needs three for quorum, so either site can fail without losing quorum. The QDevice connects to the cluster over TCP port 5403 and doesn't have the low-latency requirement of corosync, so it can share site C with ONTAP Mediator.

=== Tie breaker alignment with the primary cluster

When the inter-site link fails but both sites can still reach site C, ONTAP keeps the primary cluster at site A serving data. The QDevice must give its vote to the same site. By default, the QDevice chooses the partition that contains the lowest node ID.

*BEST PRACTICE:* Create the Proxmox VE cluster on a site A node and join the other site A nodes before you join site B nodes, so that site A holds the lowest node IDs. If the primary storage moves to site B for an extended time, update the QDevice `tie_breaker` setting to a site B node ID.

If the QDevice favored site B instead, site A nodes would self-fence, and HA would restart VMs on site B nodes that can't reach the active storage at site A.

=== HA behavior and VM placement

* Proxmox VE HA typically detects a failed node and recovers its VMs in about two minutes, including a 60-second watchdog fencing timeout. During a site failure, the SnapMirror active sync failover and the Proxmox VE HA recovery run in parallel.
* Use HA node affinity rules with node priorities to place VMs on the nodes at the same site as their primary storage, and to let them fail over to the other site.
* After a site failover, set the HA `failback` property to `0` for affected VMs until you fail the storage back. Otherwise, HA migrates VMs back to site A nodes as soon as they return, while the active storage is still at site B.
* Make sure the guest operating system disk timeouts are longer than the expected failover time, so that guests don't report I/O errors during a storage failover.

== Integration with Storage Manager for Proxmox

Storage Manager for Proxmox (SMP) gives Proxmox VE administrators one interface to provision ONTAP shared storage and to back up, restore, and clone VMs by using ONTAP snapshots and FlexClone technology. SMP connects to the Proxmox VE cluster and to ONTAP through their APIs, so it doesn't need agents on the Proxmox VE nodes.

SMP and SnapMirror active sync protect against different kinds of failures. SnapMirror active sync keeps VMs running through a storage or site failure, but it replicates every write synchronously, including an accidental deletion, a failed guest update, or data encrypted by ransomware. SMP snapshots give you point-in-time copies to recover from those logical failures. Together, they provide continuous availability and fast operational recovery from the same ONTAP storage.

[cols="2,3,2,2" options="header"]
|===
| Protection layer
| Protects against
| Recovery point
| Managed with

| SnapMirror active sync
| Storage system failure and site failure
| Zero data loss
| ONTAP

| SMP backups (ONTAP snapshots)
| Accidental deletion, data corruption, failed updates, and ransomware
| Last scheduled or on-demand backup
| SMP

| SnapMirror asynchronous fan-out or Proxmox Backup Server
| Loss of both sites, and long-term retention
| Last replication or backup
| ONTAP or Proxmox Backup Server
|===

=== Backup and recovery

SMP creates crash-consistent or file-consistent backups as ONTAP snapshots of the storage volumes, on demand or by policy, and restores individual VMs, storage, or resource groups:

* Use resource groups and backup policies to apply the same schedule and retention to the VMs of a tenant or an application.
* Use file-consistent backups for VMs that run the QEMU guest agent, so the guest file systems are quiesced before ONTAP creates the snapshot.
* SMP manages the storage that is active. After a SnapMirror active sync failover, run a discovery in SMP so that it maps the storage to cluster B before you run backup or restore operations.
* For a third copy outside the two sites, or for longer retention, add a SnapMirror asynchronous fan-out relationship from the protected volumes, or use Proxmox Backup Server.
* Tamperproof snapshots aren't supported with SnapMirror active sync, so don't enable snapshot locking in SMP for protected volumes.

=== VM cloning

SMP uses ONTAP FlexClone technology to create space-efficient VM clones for development, testing, and rapid provisioning. Clones that you create in protected storage consume replication bandwidth and capacity at both sites. Exclude clones and test storage that don't need business continuity from SnapMirror active sync protection.

=== SMP placement

* Run the SMP VM as an HA resource on a SnapMirror active sync protected shared storage, so that SMP stays available after a storage or site failure.
* Register the Proxmox VE cluster and both ONTAP clusters in SMP, so that SMP can reach the active storage at either site.

== NFS shared storage with SnapMirror active sync for NAS

Beginning with ONTAP 9.19.1, SnapMirror active sync protects NAS workloads. The following considerations apply only to NFS shared storage. To deploy the solution with NFS storage, follow the link:proxmox-active-sync-nas-config.html[NAS configuration workflow].

=== SVM-level protection and network identity

* SnapMirror active sync for NAS protects an entire storage VM (SVM). You can protect all volumes in the SVM or exclude selected volumes. Only FlexVol volumes are supported, and the SVM can't contain LUNs.
* The secondary SVM stays dormant, with its LIFs down, until a failover. ONTAP replicates the SVM configuration, including LIF IP addresses, export policies, and NFS settings, so the secondary SVM presents the same NFS endpoint after a failover.
* Failover is non-disruptive for NFSv3 and later.
* SnapMirror active sync for NAS is active/passive, so VMs on site B nodes read and write across the inter-site network to the primary SVM. For active workloads at both sites, use two SVMs with opposite replication directions, one primary at each site, and align each VM's node affinity rule with the site of its primary SVM.
* SnapMirror active sync for NAS is supported on AFF A-Series and C-Series two-node clusters.

=== NFS client settings

Use NFSv3 or NFSv4.1 for the NFS storage. Keep the default hard mount behavior, and don't add the `soft` mount option, so that NFS I/O retries instead of failing during a failover.

=== NFS storage provisioning with SMP

SMP provisions an ONTAP volume, creates or selects an export policy, and mounts the volume as NFS shared storage on the Proxmox VE nodes that you select. For storage in a protected SVM:

* Provision the volume in the primary SVM, and select the NFS LIF, or the VIP LIF in a layer 3 network, as the preferred LIF. The secondary SVM uses the same address after a failover, so the storage definition stays valid.
* Mount the storage on all Proxmox VE nodes at both sites so that HA can restart VMs on any node.
* Make sure the export policy allows the Proxmox VE nodes at both sites. ONTAP replicates the export policy to the secondary SVM.
* After provisioning, verify that the volume is included in SnapMirror active sync protection.

=== Layer 3 networks with VIP LIFs and BGP

SnapMirror active sync for NAS requires the same IP address on the primary and secondary SVMs. When the NFS VLAN is stretched between sites, the LIF IP address moves with the SVM. When the sites are connected by a routed layer 3 network, the subnet of a site A LIF doesn't exist at site B.

ONTAP virtual IP (VIP) LIFs solve this problem. A VIP LIF doesn't belong to any subnet. ONTAP advertises the VIP address to the peer routers as a /32 host route by using Border Gateway Protocol (BGP), so the address can move between sites without a stretched VLAN.

image:proxmox-business-continuity-004.png["VIP LIF for NFS shared storage advertised through BGP from the active site in a layer 3 network. The numbered items are described after the diagram."]

. Each node at both sites has BGP LIFs in the system SVM that peer with the routers at its site. BGP LIFs are node specific and aren't replicated, so you configure them on both clusters.
. The primary SVM hosts the NFS VIP LIF. Cluster A advertises the /32 host route, and the Proxmox VE nodes at both sites reach the storage through the routed network.
. After a SnapMirror active sync failover, the VIP LIF comes up on the secondary SVM, cluster B advertises the host route, and the routers converge on site B.

When you plan BGP in ONTAP for the first time, it helps to know which SVM owns each LIF. BGP LIFs belong to the system SVM of the IPspace, not to the data SVMs. One set of BGP LIFs on each cluster serves the VIP LIFs of every data SVM in that IPspace, so you don't create BGP LIFs for each tenant. The following diagram shows the LIF and port layout on one cluster, with BGP LIFs on VLAN ports.

image:proxmox-business-continuity-005.png["BGP LIFs in the system SVM of an IPspace, homed on VLAN ports, serve the VIP LIFs of all data SVMs in the IPspace. The numbered items are described after the diagram."]

. Each node has two ports for BGP, in this example the VLAN ports `e0c-100` and `e0d-200`. Each port connects directly to a different router.
. Each node has two BGP LIFs in the system SVM, one on each port, with a /31 subnet and a BGP peer group to one router. For the Default IPspace, the system SVM is the cluster SVM. For a custom IPspace, it's the SVM with the same name as the IPspace.
. Data SVMs in the same IPspace host VIP LIFs and don't need BGP LIFs of their own. The BGP peer groups advertise the VIP routes for all SVMs in the IPspace.
. ONTAP creates a VIP port, for example `v0a`, on each node when you create the first BGP peer group. VIP LIFs are hosted on the VIP port and are reachable through every port on the node that hosts a BGP LIF in the IPspace.

The home port of a BGP LIF can be a physical port, a VLAN port, an interface group, or a VLAN on an interface group. An interface group isn't required. NetApp Technical Report TR-4949 recommends two BGP LIFs on two separate ports for each IPspace, each directly connected to a different first-hop router.

Keep the following guidelines in mind:

* BGP LIFs don't fail over. Redundancy comes from two BGP LIFs per node, each peering with a different router. If a node loses all its BGP sessions for an SVM, ONTAP moves the VIP LIF to another node that has an active BGP session for that SVM.
* Use external BGP (eBGP) with a unique private autonomous system number (ASN) for each ONTAP node and each router.
* Use a /31 subnet (netmask 255.255.255.254) for each BGP LIF and its router. Assign the odd-numbered address to the BGP LIF and the even-numbered address to the router.
* ONTAP doesn't process routes from the routers. Configure the routers to accept /32 host routes from ONTAP and not to send route updates to the cluster.
* Proxmox VE nodes must not share a subnet with the VIP address. A redundant layer 3 router, for example with VRRP or HSRP, must be in the path between the nodes and the storage.
* Configure BGP peer groups with `-use-peer-as-next-hop true` so that each cluster learns its default route from its local routers. Routes that point to a site A gateway aren't valid at site B after a failover.
* Enable multipath routing so that outgoing VIP traffic uses all available BGP LIF ports.
* Lower the BGP hold time from the default of 180 seconds. TR-4949 recommends a hold time of 3 seconds. A router withdraws the route from a failed cluster only when the hold timer expires, and during a storage system failure the router at site A stays online.
